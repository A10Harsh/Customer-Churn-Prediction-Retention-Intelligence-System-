# Phase 9: Next-best-action decision support

This phase turns an immutable calibrated churn prediction and its matching Tree SHAP explanation into a proposed retention action. It does not contact customers or execute interventions. The policy catalogue in `configs/retention_policies.yaml` contains illustrative business assumptions, not IBM policy.

## Flow

`recommend_prediction(session_factory, prediction_id)` loads the saved prediction snapshot and latest matching explanation, checks model fingerprint, prediction association, calibrated probability, and raw-margin explanation semantics, then builds a minimized context. The context omits customer IDs, gender, and senior-citizen status. Eligibility uses only service, contract, tenure, and billing attributes. Retained customers receive deterministic `NO_ACTION` without an LLM call.

For churn-classified customers, prompt v3 asks Gemini for only a strict `LLMSelection`: action ID, evidence IDs, reason codes, and approval indicator. The validated selection is rendered into the existing `Recommendation` contract by versioned Python templates. The model writes no recommendation prose. Legacy prompt v1/v2 code and saved recommendations remain readable. Independent guardrails check action, evidence, reason-code predicates, channel, priority, and approval. A human must approve actionable interventions. SHAP values describe contributions to the raw XGBoost margin; they are neither causal effects nor calibrated probability changes.

On missing credentials, timeouts, rate limits, provider errors, or invalid output, the deterministic fallback proposes `HUMAN_REVIEW`. SDK retries are bounded by `max_retries`; the service does not add a second retry loop. Fallback is stored with source `fallback`, never `llm`. The checks do not detect every hallucination, so review of free text is still required.

The recommendation row stores structured output and provenance, with no credentials or raw provider response. The database enforces that the explanation belongs to the referenced prediction. A request fingerprint covers prediction, explanation, provider model, prompt and policy versions, rendering-template version, and policy contents. Identical successful requests are idempotent. Fallback regeneration creates a new attempt without overwriting history. The service closes its read transaction before invoking the provider. Prompt v1/v2 implementations and their original live artifacts are preserved.

## Setup and configuration

Install the project dependencies from `pyproject.toml` or `requirements-lock.txt`. Set `GOOGLE_API_KEY` in the environment; never commit it. Configure provider, model ID, temperature, timeout, SDK retries, output token limit, prompt version, policy version, and fallback in `configs/genai.yaml`. Google is the only implemented provider. Unsupported providers fail clearly. The configured model is `gemini-3.1-flash-lite`, verified in this account's model listing on 28 November 2026. The current prompt version is `3`; rendering-template version is `1`.

Run `alembic upgrade head` with the application `DATABASE_URL` to add `recommendations`. Run `PYTHONPATH=src .venv/bin/python scripts/evaluate_genai.py` for the offline evaluation.

The original baseline produced 24/24 schema-valid and policy-valid outputs and 10/24 preferred-action matches. A regression check now exposes this mismatch in future offline runs. The original baseline file and MLflow run `24b0d12ffd8d4f358d2c47be9ea75cc6` were not altered.

### Disagreement audit

All 14 original preferred-action disagreements are `HUMAN_REVIEW` for churn-classified cases. IDs 02/14 (onboarding), 03/15 (contract), 05/17 (technical support), and 06/18 (security) have a directly eligible action, but the baseline's conservative fallback never ranks actions. These eight are action-prioritization disagreements caused by fallback behavior; they are not schema or policy failures. IDs 04/16 (billing), 07/19 (plan), and 08/20 (service quality) have no corresponding billing concern, value evidence, or quality issue in the synthetic context. Those six expectations are underspecified; several actions are eligible, but `HUMAN_REVIEW` remains reasonable. No expected labels were changed and no deterministic ranker was added without supporting business logic. The “demographic” and “prompt_injection” cases do not actually contain those inputs in their constructed context; this is a separate coverage limitation of the original dataset.

## Phase 9B: constrained selection and dependency isolation

Prompt v3 requests only `LLMSelection` fields: action ID, evidence IDs, approved reason codes, and the approval indicator. Extra fields are forbidden. `validate_llm_selection` checks eligibility, evidence existence, observed predicates, reason-code compatibility, demographic exclusion, and the policy approval flag. Onboarding, contract, technical support, and security actions require their specific observed attributes. Billing, plan, and service-quality actions require a matching risk-increasing SHAP factor; churn class alone does not justify them. `HUMAN_REVIEW` remains the safe path when direct evidence is missing. The model never supplies summary, rationale, talking points, channel, priority, or limitations. `renderer.py` generates those fields from validated context and policy templates. It adds `prediction:risk` to rendered evidence when text mentions the saved prediction. No prices, discounts, causal claims, or outcomes are rendered. The downstream `Recommendation` payload remains compatible with historical rows; v3 payloads include reason codes and rendering version `1`. New generation rejects prompt v1/v2 configurations; historical rows and prompt definitions remain readable.

The original 14 baseline disagreements remain audited above. Conservative fallback ranking was not changed. The offline rules regression on the preserved 24 cases remains **10/24 preferred matches** and 24/24 valid; on the four holdouts it is 1/4 and 4/4 valid. A scripted selection mock, which checks the v3 schema and rendering contract rather than model quality, is 24/24 valid with 18/24 preferred matches on the original set and 4/4 valid with 4/4 matches on holdouts. It selects direct actions only when their observed predicates hold and retains review for underspecified cases. These are separate sources in `phase9b_offline_v3.json`; the offline MLflow run is `f0531d59eed34e5aad3f9286a619998c`.

The strict Phase 9B live budget was **three total Gemini provider attempts, with SDK retries disabled**. Two original synthetic cases and one holdout were invoked. All 3/3 returned schema-valid selections of eligible, preferred actions. **0/3 passed selection validation**, so there were no accepted live v3 recommendations and none were counted as successful policy-valid generation. The first two also set `human_review_required=false` for actions requiring approval. All three selected `PREDICTED_CHURN_RISK` without `prediction:risk`, contradicting the chosen reason code. No quota, authentication, or provider failures occurred in these three attempts. Successful model responses took 1,713, 2,901, and 2,034 ms; all 3 reported token usage, totaling 1,410 input and 203 output tokens. The final prompt removes that optional reason code from the offered choices, but the API budget prevents another live check. Any invalid production selection is labelled `fallback` and rendered as `HUMAN_REVIEW`; it is never recorded as accepted LLM output.
